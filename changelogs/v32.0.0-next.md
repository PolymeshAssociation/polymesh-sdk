This guide describes **unreleased** changes for the next major version, **v32.0.0**, of `@polymeshassociation/polymesh-sdk`. If you're upgrading, start with the [Quick migration checklist](#quick-migration-checklist) below.

---

## Overview

v32.0.0 is a **major release**. Every middleware (SubQuery) query moves to the **redesigned SubQuery schema**, and the SDK requires a middleware that runs it. The redesign replaces string relations with id columns, stamps each row with the event that created and last updated it, splits POLYX history into one entry per side, and indexes events by what they involve rather than by argument position.

**Key themes in this release:**

- **Redesigned middleware required.** Queries against an older middleware fail.
- **Middleware enums follow the new schema.** OrderBy values and re-exported enums changed.
- **Settlement affirmations are per holder.** An Instruction lists one affirmation for every portfolio or Account on its legs, from the moment it is created.

---

## Prerequisites

### Supported middleware versions

The middleware must run the redesigned SubQuery schema: `polymesh-subquery` `v20.0.0-alpha.1` or later. Methods that use the middleware fail against an older one, with GraphQL validation errors.

---

## Quick migration checklist

1. Upgrade the middleware to the redesigned SubQuery schema before upgrading the SDK.
2. Replace `CREATED_BLOCK_ID_*` OrderBy values with `CREATED_EVENT_ID_*`, and drop `EVENT_IDX_*` ones (see [Middleware enums](#1-middleware-enums-follow-the-new-schema)).
3. Replace `TickerExternalAgentActionsOrderBy` with `AssetAgentActionsOrderBy`.
4. Review code that reads `Instruction.getAffirmations()` (see [Affirmations are per holder](#3-instructiongetaffirmations-lists-every-holder)).
5. Move code that reads `account.getPolyxTransactions()` to the per-side entries (see [POLYX history](#4-polyx-history-is-one-entry-per-side-of-a-movement)).
6. Read `ExtrinsicData.params` as an object keyed by argument name (see [Extrinsic params](#5-extrinsic-params-is-an-object-keyed-by-argument-name)).
7. Read `nftCount` from `getHeldNfts()` and `assetHolders.get()`, list NFTs with `identity.getHeldNftsOfCollection()`, and replace `NftHoldersOrderBy` with `AssetHoldersOrderBy` (see [NFT holdings](#6-nft-holdings-return-a-count-a-new-method-lists-the-nfts)).
8. Replace `eventArg0`–`eventArg2` with `refs` or `args` in `getEventByIndexedArgs` and `getEventsByIndexedArgs` (see [Events](#7-events-are-found-by-what-they-involve-not-by-argument-position)).
9. Handle `null` `txTag` and `args` from `multiSig.getHistoricalProposals()` (see [Historical MultiSig proposals](#8-a-historical-multisig-proposal-may-have-no-known-call)).
10. Handle a `null` `extrinsicIndex` from `getTransactionHistory()` on fungible Assets and NFT collections.
11. Expect `NftCollection` as well as `FungibleAsset` from `identity.getTrustingAssets()`.
12. Handle a `null` `action` from `proposal.votes()`.
13. Read `portfolio.getTransactionHistory()` and `identity.portfolios.getTransactionHistory()` as a `ResultSet`, and page through it with `size` and `start` (see [Settlement history](#12-settlement-history-is-paged-and-lists-every-transfer-no-instruction-made)).

## Breaking changes

### 1. Middleware enums follow the new schema

The middleware types are regenerated from the redesigned schema. Every OrderBy enum the SDK accepts (`AssetHoldersOrderBy`, `AssetTransactionsOrderBy`, `AuthorizationsOrderBy`, `ClaimsOrderBy`, `InstructionsOrderBy`, and the others) loses its `CREATED_BLOCK_ID_*`, `UPDATED_BLOCK_ID_*` and `EVENT_IDX_*` values and gains `CREATED_EVENT_ID_*` and `UPDATED_EVENT_ID_*`. A `createdEventId` is `<block>/<event index>`, zero padded, so it orders rows by block and then by event, as the two old keys did together.

The `CREATED_AT_*` values the SDK adds to every OrderBy enum still order by creation.

### 2. Asset agent history uses the new agent tables

`identity.assetPermissions.getOperationHistory` takes `orderBy` as `AssetAgentActionsOrderBy` instead of `TickerExternalAgentActionsOrderBy`.

### 3. `Instruction.getAffirmations()` lists every holder

The middleware keeps one affirmation row for every portfolio and Account on an Instruction's legs, from the moment the Instruction is created. When the middleware is available, `getAffirmations()` therefore lists every holder:

- holders that have not affirmed yet are listed with `AffirmationStatus.Pending`. The chain path, used without a middleware, still lists only the holders that have affirmed;
- an Identity with several portfolios on the legs appears once per portfolio, and the new `portfolio` field says which;
- a claimed off-chain receipt is listed with the Identity that claimed it as the party, and no `portfolio`;
- mediators are not listed; `getMediators()` returns them;
- a rejection is no longer an affirmation status. Use `getStatus()` to find whether the Instruction was rejected.

```typescript
const { data } = await instruction.getAffirmations();

data.forEach(({ party, portfolio, status }) => {
  // party: the Account, or the Identity owning `portfolio`
});
```

### 4. POLYX history is one entry per side of a movement

`account.getPolyxTransactions()` reads the middleware's POLYX ledger. Each `HistoricPolyxTransaction` is now the change one movement made to one Account's balance, instead of a transfer with a sender and a receiver:

| Before | After |
|---|---|
| `fromAccount`, `fromIdentity` | `account`, `identity`: the Account whose balance changed, and its Identity |
| `toAccount`, `toIdentity` | `counterpartyAccount`, `counterpartyIdentity`: the other side, when the movement has one |
| `type: BalanceTypeEnum` | `pool: PolyxPool` (`Free` or `Reserved`) |
| – | `kind: MovementKind` (`Transfer`, `Fee`, `StakingReward`, `Hold`, `Release`, …) |
| – | `direction: EntryDirection` (`Credit` or `Debit`); `amount` stays positive |
| `moduleId: ModuleIdEnum` | `moduleId: ModuleIdEnum \| undefined` |

A transfer between two Accounts of the same query now gives two entries, a `Debit` and a `Credit`. The `orderBy` option takes `PolyxEntriesOrderBy` instead of `PolyxTransactionsOrderBy`, and `BalanceTypeEnum` is no longer exported; `PolyxPool`, `MovementKind`, `EntryDirection` and `PolyxEntriesOrderBy` are.

```typescript
const { data } = await account.getPolyxTransactions({ size: new BigNumber(25) });

data.forEach(({ direction, amount, kind, counterpartyAccount }) => {
  // direction === EntryDirection.Debit: amount left this Account
});
```

### 5. Extrinsic `params` is an object keyed by argument name

`ExtrinsicData.params`, returned by `network.getTransactionByHash()` and `account.getTransactionHistory()`, is now the call's arguments keyed by name, or `null` when the middleware could not decode them. It used to be an array.

```typescript
const tx = await sdk.network.getTransactionByHash({ txHash });

// before: tx.params was an array
// after:  { assetId: '0x…', amount: '1000000', assetHolderKind: 'DefaultPortfolio' }
console.log(tx?.params);
```

Integers are decimal strings, Accounts are SS58 addresses and Identities are DIDs.

### 6. NFT holdings return a count; a new method lists the NFTs

`identity.getHeldNfts()` and `nftCollection.assetHolders.get()` return how many NFTs each collection or holder has, instead of the NFTs themselves, so one page is always one middleware request:

| Before | After |
|---|---|
| `HeldNfts.nfts: Nft[]` | `HeldNfts.nftCount: BigNumber` |
| `IdentityHeldNfts.nfts: Nft[]` | `IdentityHeldNfts.nftCount: BigNumber` |

The new `identity.getHeldNftsOfCollection({ collection, size, start })` lists, a page at a time, the NFTs an Identity holds in one collection. Given the Asset ID or ticker of an Asset that is not an NFT collection, it throws a `ValidationError`.

```typescript
const { data: holders } = await collection.assetHolders.get({ size: new BigNumber(25) });

for (const { identity, nftCount } of holders) {
  const { data: nfts } = await identity.getHeldNftsOfCollection({
    collection,
    size: new BigNumber(100),
  });
}
```

`identity.getHeldNfts()` also takes `orderBy` (and the deprecated `order`) as `AssetHoldersOrderBy` instead of `NftHoldersOrderBy`, which no longer exists.

### 7. Events are found by what they involve, not by argument position

`network.getEventByIndexedArgs()` and `network.getEventsByIndexedArgs()` no longer take `eventArg0`, `eventArg1` and `eventArg2`: the middleware no longer indexes arguments by position. They take:

- `refs`: what the event involves, in any argument, as `identity:<did>`, `account:<SS58 address>`, `asset:<asset id>`, `ticker:<ticker>` or `portfolio:<did>/<number>`. An event matches when it involves every one given;
- `args`: argument values the event must have, keyed by field name.

`moduleId` and `eventId` are still required.

```typescript
// before
await sdk.network.getEventByIndexedArgs({
  moduleId: ModuleIdEnum.Asset,
  eventId: EventIdEnum.AssetCreated,
  eventArg0: did,
});

// after
await sdk.network.getEventByIndexedArgs({
  moduleId: ModuleIdEnum.Asset,
  eventId: EventIdEnum.AssetCreated,
  refs: [`identity:${did}`],
});

await sdk.network.getEventByIndexedArgs({
  moduleId: ModuleIdEnum.Asset,
  eventId: EventIdEnum.AssetCreated,
  args: { assetId },
});
```

### 8. A historical MultiSig proposal may have no known call

`HistoricalMultiSigProposal.txTag` and `args`, returned by `multiSig.getHistoricalProposals()`, are `null` when the middleware doesn't know the proposed call: for a bridge proposal, or one made by an extrinsic that has no single proposing call for that MultiSig. Check for `null` before reading them.

### 9. `extrinsicIndex` of an Asset transaction can be `null`

`HistoricAssetTransaction.extrinsicIndex` and `HistoricNftTransaction.extrinsicIndex`, returned by `getTransactionHistory()`, are `null` for a transaction no extrinsic made, such as a settlement the chain executed at the start of a block. They used to be `NaN`.

### 10. `getTrustingAssets` returns NFT collections as `NftCollection`

`identity.getTrustingAssets()` returns `(FungibleAsset | NftCollection)[]`. An NFT collection the Identity is a trusted claim issuer for used to come back as a `FungibleAsset`.

### 11. A MultiSig proposal vote may have no known action

`MultiSigProposalVote.action`, returned by `proposal.votes()`, is `null` for a vote the middleware seeded from chain storage when its index started after genesis: from 7.0 the chain keeps that a signer voted, not which way.

### 12. Settlement history is paged, and lists every transfer no instruction made

`portfolio.getTransactionHistory()` and `identity.portfolios.getTransactionHistory()` return a `ResultSet<HistoricSettlement>` instead of `HistoricSettlement[]`, and take `size` and `start` beside their filters. They returned at most 100 instructions and 100 movements, oldest first, so an active holder's newest settlements were missing with nothing to say so.

The history is still oldest first. It merges two middleware reads, instructions and transfers, so a page is found by reading both up to its end: a later page takes more requests than an earlier one.

The history also lists the transfers between Identities that no instruction made, such as a controller transfer or a distribution payout, with their direction and no `instruction`. They changed the holder's balance but were left out. An issuance or a redemption has one side only and is still left out; `fungibleAsset.getTransactionHistory()` lists every transfer of an Asset.

```ts
// before
const settlements = await portfolio.getTransactionHistory({ assetId });

// after
const { data: settlements, next, count } = await portfolio.getTransactionHistory({
  assetId,
  size: new BigNumber(50),
  start: new BigNumber(0),
});
```

## New features

### POLYX entries carry their movement and the balance after them

Each entry from `account.getPolyxTransactions()` has:

- `movementId`, shared by the two entries of one movement, so the other side of a transfer can be found;
- `holdReason`, for an entry that holds or releases part of the balance;
- `balanceAfter.free`, `balanceAfter.reserved` and `balanceAfter.frozen`, the Account's balance right after the entry, so a balance over time can be drawn from the history alone.

### Settlement history carries the memo

A `HistoricSettlement` from `portfolio.getTransactionHistory()` and `identity.portfolios.getTransactionHistory()` has a `memo`: the Instruction's memo, or the memo of a transfer no Instruction made, such as a portfolio movement or a `settlement.transferFunds` call. It is absent when there was none.

## Modified behavior

- **Off-chain legs.** An off-chain leg has no affirmation row of its own: it is affirmed once a receipt settles it. `getOffChainAffirmationForLeg` already reads it that way.
- **Portfolio movements.** `Portfolio.getTransactionHistory` and `identity.portfolios.getTransactionHistory` read movements from the middleware's Asset transactions. NFT movements between portfolios are now listed as NFT legs. A movement includes a `settlement.transferFunds` between holders of one Identity, so either side of its leg can be an `Account` as well as a portfolio.
- **Seeded rows.** An `EventIdentifier` for something the middleware seeded from genesis or chain storage has `eventIndex` `-1`. No chain event sits at that index.
- **Leg addresses.** The `account` filter of `Portfolio.getTransactionHistory` now matches a settlement that Account signed (by creating, affirming or executing it), instead of comparing it with the whole list of signers. It selects a signer, not an Account holding the assets.
- **Ethereum-derived Account history.** `account.getTransactionHistory()` no longer throws `NotSupported` for an Ethereum-derived Account. The middleware now records a `revive.ethTransact` extrinsic under its signer's padded SS58 address, so the Account's history includes them.

## Bug fixes

### `assetPermissions.enabledAt` returns this Identity's event

It used to return the event in which the Asset's most recent agent was added, whichever Identity that was. It now returns the event in which this Identity became an agent of the Asset.

### Settlement history reports the right direction

`portfolio.getTransactionHistory()` and `identity.portfolios.getTransactionHistory()` reported a leg the portfolio or Identity sent as `Incoming`, and one it received as `Outgoing`. A sent leg is now `Outgoing` and a received one `Incoming`. For the default portfolio, a leg of another portfolio of the same Identity also had a direction; it is now `None`.

A portfolio's history now reports direction from that portfolio's side, as it did before settlements V2: a movement out of it is `Outgoing` and one into it `Incoming`, even when the other side belongs to the same Identity. Movements were always `None`. An Identity's history still gives a movement between its own holders no direction.

### Historical instructions filter by an Identity and a party together

`getHistoricalInstructions({ identity, party })` threw a GraphQL error, because both conditions were written into one filter object, which can name a field only once. Each now has its own clause, so the result is the instructions both Identities are parties to.

### A distribution's payment history leaves out the reclaim

The middleware stores a reclaim as a payment to the agent who took back what remained, so `distribution.getPaymentHistory` listed it as a payment to that agent and counted it in the total. Reclaims are now left out.

### Editing or revoking a claim checks its issuer on chain

`claims.editClaims` and `claims.revokeClaims` checked that the signing Identity issued each claim by reading the middleware, and only refused a claim that another Identity had issued. A claim nobody had issued passed, the check read at most one page of the targets' claims, and it was skipped when the middleware was unavailable. Each claim is now looked up on chain under the signing Identity, so the check needs no middleware and refuses any claim the signer has not issued. The error's `data` lists them as `claimsNotIssuedBySigner`, where it was `claimsByOtherIssuers`.

### Reads that need every row are no longer cut short

The middleware returns at most 100 rows a request by default (its `--query-limit`, which an operator can change and the SDK cannot read). Some methods read with one request and so dropped the rest without saying so:

- `identity.getTrustingAssets` read at most 100 trusting Assets.
- `asset.getOperationHistory` read at most 100 agent history entries.
- `claims.getIdentitiesWithClaims` and `claims.getTargetingClaims` page by target and by issuer, but read at most 25 claims for the whole page, the default page size.

Each now reads every page, one request after another, each starting where the rows read so far end, so a lower or higher limit reads every row too. If the middleware returns an empty page before the end it reported, the read throws a `DataUnavailable` error instead of returning fewer rows.

### An instruction read from the middleware has all of its legs

An instruction can have up to 120 legs: 10 fungible, 100 NFT and 10 off-chain. The middleware returns at most 100 of them inside an instruction, so `getHistoricalInstructions` on an Identity, a Venue or `settlements` could miss legs. The legs of an instruction with more than 100 are now read on their own.

### Middleware dates are read as UTC

The middleware stores dates in UTC and sends them with no zone marker, so they were read as local time and shifted by the reader's offset. Event and block dates, `Instruction.details()` trade and value dates, authorization expiries, mediator affirmation expiries and distribution payment dates are now read as UTC.

### Historical instruction trade and value dates are `Date`s

`getHistoricalInstructions()` on an Identity, a Venue and `settlements` returned `tradeDate` and `valueDate` as the middleware's raw string, or `undefined` when unset, although they are typed `Date | null`. They are now a `Date` read as UTC, or `null`.

### Settlement history lists an instruction once

`portfolio.getTransactionHistory()` and `identity.portfolios.getTransactionHistory()` repeated an instruction once for each of its legs that matched, each copy with all of its legs. An instruction is now listed once.

### `Instruction.getStatus()` reports the latest status

`getStatus()` checked for an executed, failed, rejected and locked event in that order, and returned the first it found. An instruction that failed and was then locked or rejected was reported as `Failed`. The status now comes from the chain, and `eventIdentifier` is the event that set it. If the middleware has not yet processed that change, `getStatus()` throws a `DataUnavailable` error rather than return an older event. An instruction settled before the chain kept statuses apart from instruction details (before Polymesh 6.0) has no status on chain, so its status comes from the middleware. An instruction that does not exist throws `DataUnavailable` with the message "The Instruction doesn't exist".

### NFT collection history returns its transactions

`nftCollection.getTransactionHistory()` queried the middleware with the SDK's form of the Asset ID rather than the middleware's, so it always returned no transactions.

### Historical instructions filter by asset

The `asset` filter of `getHistoricalInstructions()`, on an Identity and on `settlements`, queried the middleware with the SDK's form of the Asset ID rather than the middleware's, so it never matched an instruction. It now does.

### Instruction legs from the middleware are in leg order

`getHistoricalInstructions()` and the settlement history methods returned an instruction's legs in the order of the middleware's leg ids, which sort as text, so an instruction with more than ten legs listed leg 10 before leg 2. Legs are now in leg index order, as `instruction.getLegs()` returns them.

### Account transaction history filters by block

`account.getTransactionHistory()` with `blockNumber` or `blockHash` returned no transactions, because the middleware stores block ids zero padded. The filter now matches.

### Extrinsic permissions keep every pallet

Permissions in the per-pallet form, which the middleware now uses for every row, dropped a pallet given in full or with exceptions: only pallets that listed their extrinsics were read. They are all read now. This affects permissions read from the middleware, such as a historical `JoinIdentity` authorization.
